# ROYALTRICO — Product & Delivery Roadmap

Consent-based device & family monitoring. One live dashboard for the devices you own or
are explicitly authorized to monitor — transparent, auditable, revocable.

## Who it's for

| Audience | Scenario | Consent model |
| --- | --- | --- |
| **Parents** | A child's phone, enrolled with parental consent | Parent records consent; child device visible agent |
| **Couples** | Mutual or one-way location/safety sharing between partners | Bilateral accept by default; one-way allowed; either side can revoke |
| **Caregivers** | An elderly parent's device, transparent location sharing | Owner/monitored person accepts sharing |
| **Employers** | Company-issued devices under a written policy | Policy consent recorded per device |

## Core principles

1. **Consent-first** — no device is monitored without an explicit, recorded consent.
   Consent records are never generated or fabricated by the system.
2. **Transparency** — the agent is visible and removable; customers can see exactly what
   is syncing, paused, or unavailable.
3. **Auditable** — every admin action and status change is written to an audit log.
4. **Honest provenance** — every activity record carries a `source` flag
   (`agent` = reported from a real installed agent, `simulated` = generated by the
   simulation layer for demos/pilots). Admins can always tell what is real.

## Architecture

```
 real agent API ─┐
                 ├─→ ingestion pipeline → domain tables → AlertEngine → notifications → UI
 simulator ──────┘            ▲
 admin console ───────────────┴─ feature registry / statuses / audit log
```

Subsystems:

- **Customer app** — enrollment, consent, live dashboard (polling, 10–15s), activity
  tabs, alerts, in-account billing, journey status center.
- **Agent API** — token-authenticated ingestion from real devices (`/api/agent/*`).
- **Simulation layer** — scheduled generator (every minute) plus admin manual controls
  (backfill history, freeze, resume, wipe). Simulated data flows through the same models
  and UI, flagged with `source = simulated`.
- **Admin control plane** — custom Blade `/admin` area: users, devices, feature registry
  and statuses, simulation, journey steps, invoices, payment verification, content,
  audit log.
- **Journey engine** — admin-defined ordered delivery steps per customer with statuses
  (`pending → in_progress → awaiting_payment → awaiting_verification → completed`, plus
  `paused` with a reason). Admin can advance, pause (optionally suspending the customer's
  devices/features), resume, skip, or add ad-hoc steps at any time.
- **Billing & invoicing** — admin generates an invoice tied to a customer/journey step and
  attaches one or more payment methods (bank transfer, PayPal email, CashApp, crypto, …).
  The customer picks a method, pays out-of-band, and uploads proof of payment. Admin
  approves or rejects with a reason. Approval marks the invoice paid and unlocks the step.
  Invoices are shown only inside the customer's authenticated account (no public links,
  no downloads).

## Feature registry

Every advertised capability is a first-class entry in the feature registry with a status:

`live` · `simulated` · `beta` · `coming_soon` · `disabled`

Activity domains: calls, SMS/messages, GPS locations, geofence alerts, app activity,
media (photos/videos), contacts, device diagnostics, browser history, email, notes,
calendar, remote device commands (lock/ring/locate).

## Planned data model additions

`features`, `device_features`, `simulation_profiles`, `service_steps`, `device_shares`,
`consents`, `payment_methods`, `invoices`, `invoice_items`, `payments` (proof + review),
`notifications`, `plans`, `orders`, `entitlements`, `audit_logs`, `device_commands`,
plus `source` columns on activity tables and an admin role on `users`.

## Delivery phases

| Phase | Scope | Done when |
| --- | --- | --- |
| **1 — Cracks** | Device activation on first check-in, auth hardening (logout middleware, login throttle), status-dot CSS, page titles, Bootstrap pagination, `AlertFactory`, rich demo seeder, README/ROADMAP, repo cleanup | Tests green, pushed |
| **2 — Admin foundation** | `is_admin` + `/admin` gate, feature registry, `source` columns, audit log, journey steps + pause/continue controls, customer status center | Admin can change any device/feature/step status and it is audit-logged and visible to the customer |
| **3 — Domains + simulation** | All activity domains, simulator (scheduled + manual), backfill | A fresh device shows realistic data in every tab within a minute |
| **4 — Experience** | Polling live updates, notifications, sharing & bilateral consent (couples/family), QR/link enrollment, remote commands | Partner invite/accept/revoke works; dashboard updates without reload |
| **5 — Commercial** | Plans/entitlements, invoices, payment methods, proof upload + verification queue, journey gating, legal pages | Admin sets methods on an invoice at step N → customer pays + uploads proof → admin approves → step N completes and step N+1 unlocks |
| **6 — Hardening** | Rate limits, token rotation/revocation, backups, scheduler + queue in production, deployment, monitoring | Deployed, restore tested, limits verified |

## Working agreement

- One logical commit per workstream; `php artisan test` and `vendor/bin/pint --dirty`
  must pass before every commit.
- Push every commit to `origin/main`; never force-push.
- New behavior ships with tests and seeded demo data.
- No dead links and no silent empty states in the UI.
